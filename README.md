# SNP Optimizer Insight

Дашборд для анализа лога `optimizer_status` планировщика SNP: обзор прогона,
использование сущностей, ограничения и узкие места, SOFT-штрафы, история прогонов,
сырые данные и автоматические проверки качества.

Дашборд рассчитан на бизнес-пользователя: каждый раздел начинается с **вердикта**
— можно ли публиковать план и что этому мешает, — а уже затем идут показатели,
графики и детальные таблицы.

Два источника данных:

1. **XLSX-файлы** с листом `optimizer_status` (кнопка со стрелкой в шапке);
2. **PostgreSQL** — таблица `optimizer_status` в схемах `public`, `public_1`, … (кнопка с базой данных в шапке).

## Быстрый старт

```bash
npm install
npm start
# → http://localhost:3000
```

Порт и хост меняются переменными окружения: `PORT=8080 HOST=127.0.0.1 npm start`.

> Открытие `index.html` напрямую из файловой системы по-прежнему работает для
> XLSX, но подключение к Postgres требует запущенного backend (`npm start`):
> браузер не умеет открывать TCP-соединения к СУБД. Если страница открыта
> **не** через `http://localhost:3000` (двойной клик, Live Server, хостинг),
> укажите адрес запущенного backend в поле «Дополнительно: адрес backend» на
> шаге 1 модалки — при `file://` подставится `http://localhost:3000`. Backend
> разрешает CORS, поэтому запросы к нему с чужого origins работают.

## Подключение к PostgreSQL

1. Нажмите кнопку с базой данных в шапке дашборда.
2. **Шаг 1 — подключение.** Хост, порт и база уже подставлены:
   - хост: `db-postgresql-app.k8s.b1gahmn2gdjf3lsm4jeh.in-plan.ru`
   - порт: `48235`
   - база: `pgs_app_data_db`

   Достаточно ввести **только логин и пароль**. Режим SSL — «Авто» (сначала пробует
   SSL, иначе подключается без него); при необходимости выберите другой режим.

   Рядом с полем **«Пароль»** есть кнопка **«глаз»** — она показывает введённое
   значение. Используйте её, если Postgres отвечает «неверный логин или пароль»,
   хотя пароль точно верный: так сразу видно лишние пробелы по краям
   (часто бывает при копировании из документа), не ту раскладку или данные,
   подставленные менеджером паролей.

   > **Почему «по ссылке с GitHub» пароль вдруг «не тот».** Запрос в Postgres
   > всегда шлёт локальный backend, и он не зависит от того, откуда открыта
   > страница. Различаются только то, что лежит в полях: менеджер паролей
   > браузера хранит логины **отдельно для каждого сайта** — у
   > `….github.io` и у `http://localhost:3000` это разные записи, и при
   > открытии дашборда по сторонней ссылке он может молча подставить свои
   > значения. Откройте «глаз» и сверьте «Логин»/«Пароль» с теми, что
   > вводили при прямом открытии.

   Поле **«Дополнительно: адрес backend»** заполнять нужно, только если дашборд
   открыт не через `npm start` (двойной клик по файлу, Live Server, другой
   хостинг, страница по ссылке с GitHub) — без него запросы ушли бы на чужой
   статический сервер, и вместо подключения появилась бы ошибка «Ошибка
   сервера: 405». При `file://` в поле подставляется `http://localhost:3000`;
   значение запоминается между сессиями. Вставленное нормализуется: из
   markdown-ссылки вида `[http://…](http://…)` берётся сам адрес, адресу без
   схемы (`localhost:3000`) дописывается `http://`, а заведомо неверное
   значение останавливается с понятной ошибкой ещё до запроса.
3. **Шаг 2 — схемы (мультивыбор) и мэппинг столбцов.** Дашборд показывает все
   схемы, в которых есть таблица `optimizer_status` (`public`, `public_1`, …),
   с числом строк в каждой. Отметьте нужные — работает поиск по имени.

   Блок **«Мэппинг столбцов»** над списком схем показывает, какие столбцы
   таблицы приняты за поля лога. Соответствие подбирается автоматически
   по именам — включая «боевой» вариант таблицы, где имя параметра лежит
   в `status`, а значение в `message` (такие схемы доступны сразу). Ручной
   выбор нужен только для совсем других названий: тогда блок раскроется сам
   и попросит указать столбцы — подробности в разделе «Мэппинг столбцов» ниже.
4. **Шаг 3 — прогоны.** Прогоны сгруппированы по схемам, видно число строк и дату
   запуска каждого. Если прогонов ≤ 25 — выбраны все, иначе — последние 10
   в каждой схеме (по `runid`); выбор можно поменять.
5. **«Загрузить в дашборд».** Прогоны добавляются в историю и анализируются как
   обычно. Повторная загрузка тех же прогонов не создаёт дубликатов.

Подписи прогонов из Postgres содержат схему, поэтому одинаковые `runid` из разных
схем не смешиваются — ни в выборке активного прогона, ни в «Истории прогонов»,
ни в сохранённой сессии.

### Как прогон подписывается в интерфейсе

Одна длинная строка не может быть одновременно идентификатором и подписью, поэтому
у прогона четыре представления:

| Поле    | Пример                                              | Где используется                     |
|---------|-----------------------------------------------------|--------------------------------------|
| `label` | `public_1 · Прогон 22 · датасет 15 · конфиг 301 · SNP_НОЧНОЙ…` | отчёты, экспорт CSV, подсказки |
| `name`  | `SNP_НОЧНОЙ_ПЕРЕСЧЁТ_РЕГИОН_ЦЕНТР_22`               | заголовки                            |
| `short` | `#22`                                                | оси графиков                         |
| `ctx`   | `схема public_1 · прогон 22 · датасет 15 · конфиг 301` | строка контекста под селектором   |

В выпадающих списках подпись укорачивается (схема, номер и обрезанный alias),
полное имя доступно в подсказке. Селектор ограничен по ширине — раньше `<select>`
растягивался под самое длинное имя в списке и давал горизонтальный скролл.

## Мэппинг столбцов

Дашборду нужно знать, в каких столбцах таблицы лежат поля лога оптимизатора.
Соответствие подбирается автоматически по именам столбцов (регистр не важен):

| Поле дашборда      | Обязательно | Автоподбор по именам                                            |
|--------------------|-------------|------------------------------------------------------------------|
| Прогон (`runid`)   | да          | `runid`, `run_id`, `run`, `id_run`, `Прогон`                      |
| Параметр           | да          | `Параметр`, `parameter`, `param`, `metric`, `Показатель`, …; запасной: `status` |
| Значение           | да          | `Значение`, `value`, `val`; запасной: `message`                   |
| Датасет            | нет         | `datasetid`, `dataset_id`, `dataset`, `Датасет`                   |
| Конфиг             | нет         | `configid`, `config_id`, `config`, `Конфиг`                       |

`status` (имя параметра) и `message` (его значение) — так называются эти поля
в «боевой» таблице `optimizer_status` (`status, runid, datasetid, message,
update_date_time, configid, change_author, sys_id`). Это запасные варианты:
они берутся, только если нормальных названий нет, поэтому таблица с настоящими
`Параметр`/`Значение` по-прежнему распознаётся по ним. Схемы с таким видом
доступны сразу, без ручного мэппинга.

**Если автоподбор не сработал** — названия столбцов совсем другие (ни один из
вариантов выше не встретился) — блок «Мэппинг столбцов» на шаге 2 раскроется
автоматически и покажет предупреждение «нужно указать: Параметр, Значение»,
а недоступные схемы будут подписаны причиной. Дальше:

1. Выберите столбцы в выпадающих списках под нужные поля.
2. Кнопка **«Показать образцы строк»** выводит первые 5 строк таблицы со всеми
   столбцами — по ним видно, где имя параметра (`Solution`, `Result gap %`,
   `Non-zero values of …`), а где его значение.
3. Схемы, к которым мэппинг подходит, сразу становятся доступными и отмечаются
   сами (если до этого не было выбрано ни одной); те, где нужных столбцов нет,
   остаются помеченными с пояснением.
4. **«Сбросить на авто»** возвращает автоматический подбор.

Мэппинг применяется ко всем выбранным схемам, уходит в каждый запрос к backend
и запоминается между сессиями (в `localStorage`, вместе с хостом и логином).
Если в сохранённом мэппинге указаны столбцы, которых нет в новой базе, он
сбрасывается на автоподбор.

**Датасет и конфиг необязательны.** Если этих столбцов в таблице нет, оставьте
поля пустыми — прогон будет опознаваться по одному `runid`.

## Разделы дашборда

Все семь разделов построены по одной схеме: **вердикт → KPI → графики → таблица → резюме**.

| Раздел | На какой вопрос отвечает |
|--------|--------------------------|
| Обзор | Можно ли брать этот план в работу и что он даёт бизнесу |
| Использование сущностей | Сколько спроса покрыто и как задействованы производство, закупки, логистика, запасы |
| Ограничения и узкие места | Что сдерживает план и какие мощности простаивают |
| Штрафы (SOFT) | Отступления от мягких плановых целей и во что они обходятся |
| История прогонов | Улучшается или деградирует качество планирования от прогона к прогону |
| Данные | Исходные строки лога `optimizer_status` — технический срез |
| Качество и аномалии | Что не так, почему это важно и что с этим делать |

**Вердикт** — цветная плашка в начале раздела: зелёная («план можно публиковать»),
жёлтая («можно с оговорками») или красная («публиковать нельзя»), с перечислением
конкретных причин.

**KPI** сформулированы в бизнес-терминах и, если в истории есть предыдущий прогон,
показывают дельту к нему: например «Покрытие спроса 88,1% · 167 из 210 строк спроса
получили план продаж · ▲ 1,4 п.п. к предыдущему прогону». У каждого KPI есть
знак «?» с расшифровкой смысла показателя.

**Таблицы** используют фиксированную раскладку с явными ширинами колонок: длинные
значения усекаются многоточием, полный текст доступен в подсказке. По умолчанию
показаны 4–6 бизнес-значимых колонок; технические (коды ограничений, режимы
`SOFT`/`STRICT`, доли переменных модели) включаются кнопкой **«Столбцы»**.
В экспорт CSV всегда попадают все колонки, включая скрытые.

**Графики.** Высота горизонтальных диаграмм считается от числа категорий, а не от
ширины карточки. На вкладке ограничений есть диаграмма «напряжение ограничений»:
одна шкала 0–100 % на ограничение, где слева отложена доля объектов, простаивающих
у нижней границы, а справа — доля, упирающаяся в потолок.

## Какие параметры лога читает дашборд

Значения в столбце «Параметр» (у вас — `status`) разбираются так:

| Строка лога | Куда попадает |
|-------------|---------------|
| `Start time`, `Solver`, `Config`, `Config hash`, `Alias` | карточка «Как настроен прогон», имя прогона |
| `Included entities`, `Functional entities`, `Constraint types` | карточка «О прогоне» |
| `Global cost mutliplier` | карточка «О прогоне» |
| `Variables`, `Continuous vars`, `Constraints`, `Iterations` | KPI «Масштаб задачи» |
| `Solution`, `Calc time`, `Solve time` | вердикт раздела, KPI «Можно ли доверять расчёту», «Время расчёта» |
| `Objective value`, `Solution value (scaled)`, `Sum of variables values` | KPI «Экономический эффект плана», диаграмма вклада блоков |
| `Deleted variables`, `Deleted constraints` | проверка качества |
| `Non-zero values of <сущность> variables` (+ ` %`), `Value of <сущность>` | KPI «Покрытие спроса», вкладка «Использование сущностей» |
| `Lower/Upper bound reached <сущность>:<ограничение> (STRICT\|SOFT) %` | график «Что сдерживает план», вкладка «Ограничения и узкие места» |
| `Softmin/Softmax penalties sum …`, `… non-zero… %` | вкладка «Штрафы (SOFT)» |

**Необязательные строки.** `Periods`, `Result gap %`, `Nodes`, `Best bound`,
`Solver nodes` есть не в каждой выгрузке. Если их нет:

- горизонт планирования берётся из поля `periods` внутри `Config`;
- gap показывается как «н/д» с пояснением, зависящим от статуса: при `OPTIMAL`
  это линейная (LP) модель, где симплекс-метод даёт точный оптимум и зазору
  неоткуда взяться; при `INFEASIBLE` — допустимого решения нет вовсе, поэтому
  и сравнивать не с чем.
  Раньше отсутствующий gap превращался в `0,00%`, и дашборд ошибочно сообщал
  об идеальной точности; графики истории такие прогоны тоже пропускают, а не
  рисуют по ним ноль.

**Повторяющиеся параметры.** Если один и тот же параметр встречается в прогоне
несколько раз с разными значениями (например `Start time`, `Config hash` и
`Alias` пишутся на каждом этапе расчёта), дашборд использует последнее значение
и показывает расхождение отдельной проверкой на вкладке «Качество и аномалии».

Строки таблицы — в том же формате, что строки листа XLSX
(`Solution`, `Non-zero values of …`, `Lower/Upper bound reached …` и т.д.).

Лимит ответа сервера — 300 000 строк за одну загрузку; о срабатывании лимита
дашборд предупреждает.

## Безопасность

- Пароль передаётся только в теле HTTPS/HTTP-запросов к backend и хранится
  **только в памяти вкладки** — в `localStorage`/`IndexedDB` сохраняются лишь
  хост/порт/база/логин/режим SSL.
- Backend не логирует учётные данные и не хранит сессии: каждое обращение к API
  открывает собственное короткое соединение к Postgres.
- Не публикуйте backend в открытый интернет без дополнительной защиты (VPN,
  reverse-proxy с аутентификацией): знание логина/пароля Postgres даёт доступ к данным.
- Backend разрешает CORS (`Access-Control-Allow-Origin: *`, preflight
  `OPTIONS → 204`) — это нужно, чтобы дашборд мог звонить в него с чужого
  origins (включая `file://`). Куки/сессии не используются, пароль живёт
  только в теле запроса, поэтому «*» безопасно.

## API backend (`server.js`)

| Метод | Путь               | Назначение                                    |
|-------|--------------------|-----------------------------------------------|
| `GET` | `/`                | дашборд (`index.html`)                        |
| `GET` | `/api/health`      | проверка живости                              |
| `GET` | `/api/pg/defaults` | хост/порт/база по умолчанию                   |
| `POST`| `/api/pg/schemas`  | схемы с таблицей `optimizer_status`           |
| `POST`| `/api/pg/columns`  | столбцы схемы + образцы строк для мэппинга    |
| `POST`| `/api/pg/runs`     | прогоны в выбранных схемах                    |
| `POST`| `/api/pg/load`     | строки `optimizer_status` выбранных прогонов  |

`/api/pg/schemas`, `/api/pg/runs` и `/api/pg/load` принимают необязательное поле
`columns` — мэппинг вида `{"run":"runid","param":"status","value":"message","ds":"","cfg":""}`.
Он приоритетнее автоподбора; пустая строка у `ds`/`cfg` означает «столбца нет».

Ошибки возвращаются как JSON `{"error": "человекочитаемый текст"}`:
`401` — неверный логин/пароль, `502` — нет соединения с Postgres и т.д.

## Тесты

```bash
npm test              # парсер + backend + UI модалки Postgres через jsdom
npm run check         # синтаксис index.html <script> и server.js
node tests/ui-audit.js  # аудит UI: отрисовка всех вкладок на граничных наборах
```

`tests/ui-audit.js` не входит в `npm test` — это отдельная проверка интерфейса
через jsdom: все 7 вкладок × светлая/тёмная тема на граничных наборах данных
(минимальный лог из двух строк, `INFEASIBLE` без gap, 12 прогонов, имя прогона
из 96 символов, сессия без новых полей), инварианты вёрстки таблиц
(`table-layout:fixed`, явные ширины колонок, усечение с подсказкой),
переключатель столбцов, навигация по прогонам и дельты KPI.
