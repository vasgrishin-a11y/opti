# Полное ревью кода `index.html` — SNP Optimizer Insight

**Дата:** 2026-09-04
**Объект:** одностраничное приложение (SPA) для анализа лога `optimizer_status` планировщика SNP.
**Стек:** чистый HTML + CSS + JS, SheetJS (XLSX) через CDN, Canvas для графиков.

---

## 1. Итоговая оценка

Приложение функционально продумано: есть обзор, разрез по сущностям, ограничениям, штрафам,
истории, сырым данным и автоматическим проверкам качества. Логика бизнес-выводов хорошая.

Но при первом запуске на реальных данных два ключевых раздела — **«Ограничения и узкие
места»** и **«Штрафы (SOFT)»** — оказались **полностью неработающими** из-за ошибки в
регулярных выражениях. Это главный баг, который вёл пользователя к неверному выводу
«данных нет», хотя данные в файле есть.

Итог: **критический баг исправлен**, добавлены понятные уведомления вместо браузерных
`alert`, drag-and-drop загрузка, защита от недоступного `localStorage`, базовая
доступность и ряд мелких улучшений.

## 2. Критические баги (исправлены)

### 2.1. Парсер границ и штрафов не распознавал данные

В `buildRun()` регулярные выражения для «Lower/Upper bound reached» и «Softmin/Softmax
penalties» содержали лишние символы:

```js
// Было (не работает):
/^Lower bound reached (\w+):(\w+) $([A-Z]+)$ %$/   // лишний пробел и $ перед пробелом
/^Softmin penalties sum (\w+):(\w+) $([A-Z]+)$$/    // нет экранированной скобки

// Стало (работает):
/^Lower bound reached (\w+):(\w+) \(([A-Z]+)\) %$/
/^Softmin penalties sum (\w+):(\w+) \(([A-Z]+)\)$/
```

**Доказательство.** Скрипт с фактическими строками демо-набора:

```
Ни один из паттернов не совпал.
После исправления: bounds = 6, penalties = 1 (production:aggregated_production).
```

**Последствие до фикса:** вкладки «Ограничения и узкие места» и «Штрафы (SOFT)»
всегда показывали:
- «Нет данных по границам»
- «Мягких нарушений не обнаружено»

Хотя данные в файле были. Пользователь получал **ложный положительный вывод «всё
хорошо»** и не видел ключевые риски (узкие места мощности, мягкие нарушения).

Это исправлено: `bounds` и `penalties` теперь парсятся из всех стандартных строк.

### 2.2. Ошибочный парсинг синего канала в `onFill()`

```js
// Было: b = parseInt(h.slice(4,6),16) — считывал перекрывающийся сегмент.
// Стало: b = parseInt(h.slice(5,7),16) — корректный синий канал.
```

Из-за этого контраст текста внутри секторов пончатов рассчитывался неверно (например,
`#1ba84c` давал синий `132` вместо `76`), поэтому цвет подписи мог быть нечитаемым на
некоторых цветах.

### 2.3. Выпадение сущностей, у которых есть только `%` использования

Фильтр `total>0 || value!==0` отбрасывал блок, если в логе есть только строка
`Non-zero values ... %`, но нет строки `Non-zero values ...` с «N / M». Добавлено
условие `|| pct>0`.

## 3. Ошибки UX / «пользовательских» багов (исправлены)

### 3.1. `alert()` при ошибках загрузки

Браузерные `alert` блокируют интерфейс и плохо выглядят. Заменены на ненавязчивый
toast-баннер + понятный статус в шапке.

### 3.2. Неинформативное сообщение о количестве добавленных прогонов

Раньше писалось «Загружено: N прогон(ов)» даже если все дубликаты и ничего нового не
добавилось. Теперь показывается:
`Добавлено: X из Y` и отдельно `повторных (уже в истории): Z`.

### 3.3. Молчаливый fallback на «первый лист» файла

Если листа `optimizer_status` нет, приложение раньше просто читало первый лист без
предупреждения. Теперь пользователь видит:
`лист optimizer_status не найден — прочитан первый лист`.

### 3.4. Утечка `Blob`-URL при экспорте CSV

`URL.createObjectURL()` раньше не освобождался. Добавлен `URL.revokeObjectURL()` и
надёжная вставка ссылки в DOM для Safari.

### 3.5. Крах при недоступном `localStorage`

В приватном режиме / при отключённых cookies вызов `localStorage` в самом начале мог
бросить исключение и **уронить весь скрипт**. Обёрнуто в `lsGet`/`lsSet` с try/catch.

## 9. Подключение к PostgreSQL (сессия arena/01a07bcb-opti)

Дашборд научился загружать `optimizer_status` напрямую из Postgres: выбор любой
схемы из мультивызбора (`public`, `public_1`, …) и таблицы `optimizer_status`
внутри неё. Для подключения достаточно ввести только логин и пароль — хост
(`db-postgresql-app.k8s.b1gahmn2gdjf3lsm4jeh.in-plan.ru:48235`) и база
(`pgs_app_data_db`) уже подставлены.

### 9.1. Архитектура

Браузер не умеет открывать TCP к Postgres, поэтому добавлен минимальный backend:

- **`server.js`** (Express + `pg`): раздаёт `index.html` и проксирует три вызова —
  `POST /api/pg/schemas` (схемы с таблицей `optimizer_status` + число строк),
  `POST /api/pg/runs` (прогоны с числом строк и `Start time`),
  `POST /api/pg/load` (нормализованные строки выбранных прогонов, лимит 300 000).
  Плюс `GET /api/health` и `GET /api/pg/defaults`. Запуск: `npm start`.
- **Клиент (§16 в `index.html`)**: кнопка с базой данных в шапке → 3-шаговая
  модалка (подключение → мультивыбор схем → выбор прогонов по схемам) → слияние
  с историей как при загрузке XLSX (дедупликация, сортировка, персистентность).

### 9.2. Модель данных (обратно совместимо)

- `parseOptimizerRows` читает необязательное поле `__schema`/`schema` и включает
  его в ключ группировки; `buildRun` кладёт схему в `r.schema` и в подпись
  (`public_1 · Прогон 19 · …`); `runKey` — `schema|runid|dsid|cfgid` при наличии
  схемы, иначе как раньше. Файловые прогоны и старые сессии ведут себя как прежде.
- Сервер сопоставляет столбцы таблицы регистронезависимо (русские/английские
  имена), все идентификаторы квотирует, значения передаёт только параметрами.
- Схемы с неподходящей структурой таблицы помечаются недоступными с причиной,
  а не роняют подключение.

### 9.3. Безопасность

- Пароль живёт только в памяти вкладки (`PG.conn`), в `localStorage` пишутся лишь
  хост/порт/база/логин/SSL; backend не логирует и не хранит учётные данные.
- Соединения короткие, по одному на API-вызов; statement timeout 180 с.

### 9.5. «Ошибка сервера: 405» при подключении к Postgres

**Симптом:** при попытке подключиться из модалки появлялась
«Ошибка сервера: 405».

**Причина.** 405 (Method Not Allowed) **не выдаёт наш backend**: для своих
API-путей Express отвечает либо 200/JSON-ошибкой, либо 404. Эту ошибку
возвращал *чужой* HTTP-сервер — дашборд был открыт не через `npm start`
(двойной клик по `index.html`, Live Server, статический хостинг), и
`POST /api/pg/schemas` долетал до статического сервера, который не умеет
обработать POST. Ситуацию усугубляло то, что backend не разрешал
кросс-ориджинные запросы (CORS отсутствовал): preflight `OPTIONS`
получал 404, а на реальные ответы не было `Access-Control-Allow-Origin` —
браузер блокировал их, и даже верно указанный адрес backend не помог бы.

**Исправление.**

1. **CORS в `server.js`.** Middleware на всех ответах ставит
   `Access-Control-Allow-Origin: *` (безопасно: без куки и сессий, пароль
   только в теле запроса), `Allow-Methods: GET, POST, OPTIONS`,
   `Allow-Headers: Content-Type`, а preflight `OPTIONS` отвечает `204`
   сразу. Проверено вживую: `OPTIONS /api/pg/schemas → 204` с заголовками,
   POST-ответ несёт `Access-Control-Allow-Origin: *`.
2. **Поле «Дополнительно: адрес backend» на шаге 1 модалки.** Дашборд
   работает, даже если `index.html` открыт двойным кликом или лежит на
   другом хостинге: достаточно вписать, где запущен backend. При `file://`
   в поле автоматически подставляется `http://localhost:3000`. Значение
   сохраняется в `localStorage` (`snp_opt_pg.backend`), хвостовый `/`
   отбрасывается; пустое поле = запросы относительные (как раньше).
3. **Понятная ошибка вместо «Ошибка сервера: 405».** На 405/404 модалка
   объясняет, что запрос не дошёл до сервера `npm start`, а ушёл на
   обычный статический сервер, и даёт два пути решения: открыть дашборд
   через `http://localhost:3000` (после `npm start`) либо указать адрес
   запущенного backend в поле на шаге 1. Прочие не-JSON ответы получают
   пометку «ответ не JSON — вероятно, запрос пришёл не на backend».
4. **Починен повреждённый хвост `index.html`** — в репозиторий попала
   лишняя строка `cript>` и дубликаты `</body></html>` после настоящего
   конца документа (браузер рисовал лишний текст «cript>» в конце
   страницы).

**Тесты.** `tests/server.test.js` — §12: preflight `OPTIONS → 204` с
заголовками + CORS-заголовок на `GET /api/health` и `GET /api/pg/defaults`
(66 → 72). `tests/pg-ui.test.js` — §9: 405 от статического сервера →
дружелюбный текст с подсказками (остаёмся на шаге 1); §10: запросы уходят
на указанный адрес backend, значение запоминается; §11: `file://` → поле
автоматически заполнено `http://localhost:3000` (32 → 39). Итого
`npm test`: 63 + 72 + 39 = 174.

**Быстрое решение для пользователя прямо сейчас:** запустить `npm start`
и открыть дашборд через `http://localhost:3000` — 405 исчезнет. Либо вписать
`http://localhost:3000` (или реальный адрес backend) в поле
«Дополнительно: адрес backend» и повторить подключение.

### 9.6. Мэппинг столбцов: таблица `optimizer_status` с другими именами столбцов

**Симптом.** При подключении к боевой базе все схемы помечались как
недоступные:

> недоступна: Схема «public_1841» и другие схемы: в таблице optimizer_status
> не найдены столбцы: Параметр/parameter, Значение/value. Найдены: status,
> runid, datasetid, message, update_date_time, configid, change_author, sys_id.

**Причина.** Соответствие «столбец таблицы → поле лога» было зашито в код:
`mapColumns` искала строго `Параметр`/`parameter` и `Значение`/`value`. В этой
базе те же данные лежат в `status` (имя параметра) и `message` (значение),
плюс есть служебные `update_date_time`, `change_author`, `sys_id`. Подобрать
имена было невозможно, а изменить их в чужой БД — тем более, поэтому дальше
шага 2 пользователь не проходил вообще.

**Исправление.**

1. **Мэппинг стал данными, а не константой.** `COL_CANDIDATES` расширен
   (`param`: `param`, `metric`, `Показатель`, `attribute`; `run`: `id_run`,
   `Прогон`; и т.д.), а `mapColumns(columns, where, override)` принимает
   пользовательское соответствие, которое приоритетнее автоподбора.
   Новая `suggestColumns()` возвращает догадку, ничего не бросая, — она
   нужна UI, чтобы предзаполнить форму.
2. **`datasetid`/`configid` стали необязательными.** Раньше их отсутствие
   валило запрос; теперь прогон опознаётся одним `runid`, а в SQL вместо
   недостающего столбца подставляется `''::text` (`GROUP BY` и кортеж в
   `IN` строятся только по реально существующим столбцам).
3. **`/api/pg/schemas` больше не «хоронит» схему.** Если столбцы прочитаны,
   но соответствие не найдено, схема возвращается с `needsMapping: true`,
   полным списком `columns`, счётчиком строк и частичной догадкой `mapped` —
   это чинится в UI, а не является фатальной ошибкой.
4. **Новый `POST /api/pg/columns`** — столбцы схемы + до 5 строк-образцов
   (`SAMPLE_ROWS`), чтобы пользователь глазами увидел, где имя параметра
   (`Solution`, `Result gap %`), а где значение.
5. **Блок «Мэппинг столбцов» на шаге 2 модалки.** Пять выпадающих списков
   (обязательные `Прогон`/`Параметр`/`Значение`, необязательные
   `Датасет`/`Конфиг`), заполненных реальными столбцами таблицы. Раскрывается
   автоматически, если чего-то не хватает; показывает статус («подобран
   автоматически» / «задан вручную» / «нужно указать: …»); кнопки «Сбросить
   на авто» и «Показать образцы строк». Доступность схем пересчитывается на
   лету: как только указаны `status`/`message`, схема перестаёт быть «bad»
   и её можно выбрать. Мэппинг уходит в каждый запрос к backend и хранится
   в `localStorage` (пароль по-прежнему только в памяти вкладки); если
   сохранённые столбцы в новой базе отсутствуют — сбрасывается на авто.
6. **Понятные тексты ошибок.** Вместо «не найдены столбцы: …» —
   «не удалось определить столбцы: … Задайте соответствие вручную в блоке

### 9.7. Сверка мэппинга с реальным содержимым таблицы

Пользователь прислал полный перечень столбцов и все 54 строки `status` из
боевой таблицы. Прогон этого набора через парсер выявил четыре расхождения —
мэппинг столбцов (§9.6) их не покрывал, потому что проблема была уровнем
глубже: в разборе самих строк лога.

**1. Отсутствующие показатели превращались в нули (главное).**
В выгрузке нет строк `Periods`, `Result gap %`, `Nodes`, `Best bound`,
`Solver nodes` — модель линейная, у неё нет ни зазора оптимальности, ни
дерева поиска. `numv()` возвращала для них `0`, и дашборд утверждал:
«Точность решения (Gap) — 0,00%, зелёный, результату можно доверять как
практически оптимальному». Это выдумка: показателя в данных нет.

Введена `numvN()` — возвращает `null` вместо `0` для отсутствующих полей.
`gapPct`, `nodes`, `bestBound`, `solverNodes` теперь nullable. По всем местам
потребления:
- KPI «Точность решения (Gap)» → «—» с пояснением про LP-модель, без
  зелёной/красной окраски;
- резюме «Обзора» и проверка в «Качестве и аномалиях» объясняют, почему
  показателя нет, вместо вывода о надёжности;
- «История прогонов»: график gap скрывается, если ни в одном выбранном
  прогоне его нет; KPI дельты и сравнение A/B показывают «—», если gap
  известен не в обоих прогонах. Раньше по отсутствующим значениям рисовалась
  прямая на нуле и считались бессмысленные дельты «0,00 п.п.».

Реальный `Result gap % = 0.0` по-прежнему выводится как «0,00%» — отличие
«ноль» от «нет данных» сохранено (проверено регрессионным тестом на демо).

**2. `Periods` берётся из `Config`.** Отдельной строки нет, но JSON в `Config`
содержит `periods: 20`. Горизонт больше не показывается как «—».

**3. `Alias` игнорировался.** Единственный параметр из списка, который парсер
не читал вообще. Это человекочитаемое имя прогона — теперь оно есть в
`meta.alias`, в карточке «О прогоне», в подписи прогона (`Прогон 19 · … ·
SNP_ОСНОВНОЙ_ПЛАН`) и в HTML-отчёте. Заодно в карточку добавлены «Множитель
стоимости» и «Функциональные сущности» (последняя строка — только если
отличается от включённых).

**4. Дубли параметров молча схлопывались.** В выгрузке `Start time`, `Solver`,
`Config`, `Config hash` и `Alias` встречаются по 2–4 раза: лог пишется на
каждом этапе расчёта, а `runid` один. Парсер брал последнее значение и терял
факт расхождения — прогон с двумя разными `Config hash` выглядел как обычный.
Теперь конфликтующие значения собираются в `run.dups`, а на вкладке «Качество
и аномалии» появилась проверка «Повторяющиеся параметры», которая перечисляет
их (`«Config hash» (AAA111 → BBB222)`) и поясняет, что показатели относятся к
последнему этапу. Одинаковые повторы конфликтом не считаются.

Дополнительно: подпись прогона больше не содержит пустых хвостов
«· датасет · конфиг», если этих столбцов в таблице нет (следствие §9.6).

**Проверено на данных пользователя.** Все 54 строки распознаны, 5 сущностей,
2 пары границ (`production_capacity` STRICT, `stock_capacity` SOFT), 1 штраф
(нулевой Softmax отфильтрован), все 3 типа ограничений имеют русские подписи.
Все 7 вкладок рендерятся без ошибок, `NaN`/`undefined` в выводе нет.

**Тесты.** `tests/parser.test.js` — §12 полный реальный набор параметров
(Alias, nullable-поля, `periods` из Config, границы, штрафы), §13 дубли
параметров и фиксация конфликтов, §14 подписи прогона без `datasetid`/
`configid` и с Alias (63 → 90). Итого `npm test`: 90 + 112 + 66 = 268.

## 10. Автосессия БД на 4 часа + надёжность сохранения данных (сессия arena/01a08a47-opti)

### 10.1. Что просили

1. Убедиться, что данные из БД переживают закрытие/открытие вкладки.
2. Вход в БД должен жить 4 часа (+ кнопка «закрыть автосессию»): сейчас при
   переключении вкладок приходится логиниться заново.

### 10.2. Аудит: почему «выкидывает»

- `PG.conn` жил только в памяти вкладки (единственные записи — в `pgConnect`):
  перезагрузка страницы, новая вкладка браузера и выгрузка фоновой вкладки
  браузером (всё это выглядит как «переключил вкладку — надо заново») убивали
  вход. Переключение экранов внутри дашборда (`go()`/`render()`) `PG.conn` не
  трогает — отдельного бага там нет, лечится тем же механизмом.
- Данные: `persistSession`/`restoreSession` (IndexedDB) в целом корректны, но
  `serializeRuns` терял `dups` (конфликты параметров пропадали после
  перезагрузки), а провал записи (приватный режим, квота, `file://`) глотался
  молча — пользователь видел демо вместо своих данных без объяснений.

### 10.3. Автосессия (вариант A: localStorage + TTL, без изменений backend)

- Успешный вход → `pgRemember()` пишет в `snp_opt_pg` всё для переподключения:
  хост/порт/база/логин/SSL/backend/мэппинг + `enc` (пароль, base64 от UTF-8 —
  обфускация, не шифрование) + `expiresAt = now + 4 ч`.
- `pgOpen()`: живая сессия → поля подставляются, `pgAutoResume()` молча
  проверяет вход (`/api/pg/schemas`) и ведёт на шаг 2; TTL абсолютный от
  момента входа, авто-продления нет. Протухший секрет удаляется сразу.
- 401 в любом месте → секрет стирается (`pgDropStoredCreds`), пользователя
  просят ввести пароль заново.
- Кнопка «Закрыть автосессию» на шаге 1 + строка «Автовход активен до …»;
  выход через `storage`-событие гасит вход и в других вкладках origin.
- Общий финал шага 1 вынесен в `pgEnterSchemas()` (ручной вход и автовход).

### 10.4. Надёжность данных

- `dups` сериализуется; `restoreSession` проверяет `v` и чинит старые сессии.
- Ошибка записи видна: `LOAD_META.persistError`, тег «⚠ не сохранено в браузере»
  в runbar, предупреждения в тостах загрузки, `storage.persist()`,
  best-effort досохранение на `pagehide`/`visibilitychange`.

### 10.5. Тесты

- `tests/session.test.js` (новый, 16 asserts): фейк IndexedDB с shared-хранилищем —
  «закрыл/открыл вкладку» (два JSDOM), пустое хранилище → демо, недоступный
  IndexedDB → честная ошибка.
- `tests/pg-ui.test.js`: обновлены проверки «пароль не сохраняется» (§5, §13),
  новые §18 (автовход + logout) и §19 (TTL + 401).
- Итого `npm test`: 108 + 125 + 142 + 37 + 16 = 428, `npm run check` OK.
